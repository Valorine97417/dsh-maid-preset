【一】先过两道闸：值得记吗？重复吗？
闸一·值得记吗——只留「以后的会话不知道，就会踩坑、走弯路、重复问你」的信息。
- 值得记：用户偏好与红线、被纠正的错误、踩过的坑与解法、重要决定及其理由、项目现状与结论、下次还要用的路径与专有名词。
- 不值得记：一次性的操作过程、能从文件或代码现场查到的、临时的中间状态、寒暄与心情、已被后续进展覆盖的旧状态。
- 自问一句：这条三个月后在另一个会话里被检索到，还有用吗？没用就别写。
- 宁可少写：3 条扎实胜过 10 条噪音——噪音会挤占首轮注入、污染检索结果。这轮真没有值得记的，就回「无需记忆」，不要为交差硬凑。

闸二·重复吗——写之前先查重，库里已有近似的，就别再新建一条。
- 先查：用 memory_search 搜核心词；对你已经怀疑相似的条目，用 memory_find_similar 比对。
- 同一件事、同一结论 → 不要新增。只补细节或改状态，用 memory_update 改旧条目；旧条目已作废，先把它标 archived 再写新的。
- 同一件事、结论变了 → 用 memory_update 更新旧条目（保留 id，便于追溯），不要让新旧两条并存。
- 措辞不同、其实是同一件事 → 视同重复，按上面两条处理。
- 确实是两件不同的事 → 才用 memory_remember 新建；keywords 避开与旧条目完全相同的词，让两者各自可检索。
- 兜底提示：memory_remember 在内容相似度达 0.8 时会自动合并到已有条目（返回 merged），但它只看字面，分不清「同一个决定的两种说法」——查重仍然要你自己做。

1. 当前记忆库中已有的 project：{projectList}。你认为是否有新的 project 需要添加？ → 请添加新 project 的记忆。
2. 是否存在被用户纠正？被用户表扬？是否踩了什么坑，最后又是如何解决的？你要将这些存入 lesson 记忆。
- 犯的错误要记，自己的优秀表现也要记，踩的坑要记，最后如何聪明的解决了问题也要记。
- 如果是用户纠正的内容，需保留 corrected 标记；
3. 如存在以下情况，你可以酌情添加记忆条目：
- 用户是否提出了交流/工作/代码偏好 → 全局偏好记录进user；项目特定偏好进 project。

【三】回看上下文中注入的所有记忆，结合你的最新进展，请你判断，是否有需要更新的记忆？
1. 是否有哪条记忆，你现在非常确定它的信息已经过时了（比如由用户亲口否定或改变主意）？ → 你应该及时更新它的内容，不要放着不管。
2. 你是否发现有哪条记忆信息是错的，甚至误导了你？ → 更新为正确信息，或者标 archived（视为 delete）；
3. 是否有哪些todo或topic已被完成？ → 标 stale（视为 done）；
4. 你是否发现有那条记忆注入时机非常不合理，和当前任务一点关系也没有？→ 这是因为关键词不准，更新它的关键词；
5. 有没有哪条记忆其实是重复的、或已被别的条目完全覆盖？ → 保留信息最全的那条，其余标 archived；能合并的先 memory_update 合并再归档。

【四】写记忆时的通用要求
1. 写记忆的规则见系统提示词。你应该把记忆归类在正确的level和标签之下。
2. 强调一下关键词拟定标准:
- 提取 8-13 个关键词供检索
- 反向思考："在用户prompt提及哪些词的时候，你希望这条记忆能被检索到？"
- 非项目名，针对记忆本身的细节。
- 优先提取核心实体、语义中心、专有名词。
3. 如果你认为没有什么重要信息，不需要添加和更新，直接回复"无需记忆"即可，不要调用任何工具。

一轮可调用多个工具，请你尽量在一次输出中完成本任务所有的工具调用。
